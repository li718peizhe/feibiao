2. 按原顺序整理日志：处理串口工具添加的 `[hh:mm:ss] <<` 分段，只有可以确定属于同一行的片段才拼接；区分重启、日志缺段和可能的旧缓存，不丢掉故障及事件行。按 `Dart mode`、`step`、`remote`、`sw`、`online`、`arm` 等关联完整状态组；缺字段或被事件行打断时注明不确定。
3. 建立操作时间线：记录模式、拨杆和摇杆、流程步骤、摆臂角度及原始编码器、电流、转速、温度、堵转状态、推杆脉宽、磁铁状态及故障。按左侧和右侧分别标出开始、最高位置、摇杆回中、下滑或反弹及最后状态；时间戳缺失时只报顺序和相邻读数，不计算秒数或速度，遥控器离线期间的拨杆值不作为实时输入。
4. 分析摆臂：对照目标及软限位（源码左 −40.5° / 软限位 −45°，右 +46.2° / 软限位 +50°；用户现场对位另记），列出角度变化、`cmd` / `act`、`rpm`、最高 `tmp`、`stall` 和 `bus` 的变化。有时间戳且覆盖完整 5 s 时，单独计算有力、摇杆回中期间的采样角度范围和相对回中时的最大偏移，对照 5 s 不超过 1° 的保持标准；切无力后的下落单独记录，采样不足时不判定保持通过，采样点之间的瞬态无法排除。`cmd` 是限流后的指令，`±16384` 对应 `±3 A`，`4642` 约为 0.85 A；它不能单独说明控制器原始请求、积分、保持目标、瞬时峰值或物理原因。
5. 分析推杆与磁铁：`crank=...[R]` 是未标定模式下的输出脉宽，并非舵机角度反馈；`mag=0` 表示断电吸持指令，`mag=1` 表示通电消磁指令，均不能单独证明镖或继电器实际状态。按原文列出观测到的流程步骤与故障；手动操作时 `step=空闲` 可以是正常状态，打印周期约 1.16 s，短步骤可能没被采样，缺失步骤不能自动判定没有发生。
6. 先给出结论，再列关键证据及位置：哪些是日志直接观察，哪些只是可能原因，哪些需要现场确认。若出现 `stall=1`、电机离线、非“无故障”的故障、接近限位或温度异常，说明发生时的操作状态及证据；结果不足以确定成功时明确写“无法确认”。
7. 将用户的新反馈、日志路径或粘贴日志的关键原文、分析结论、验证结果和当前版本证据追加到 `handoff.md`；本任务仅修改根目录文档时，该目录没有 Git 仓库，说明无提交。
