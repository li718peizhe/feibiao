# RoboMaster 飞镖系统失联降级运行技术方案

## 1. 场景与前提

本方案讨论的是比赛现场强干扰下的极端失联场景：

```text
裁判系统数据收不到。
遥控器数据收不到。
视觉数据一定能收到。
视觉协议结构不允许修改。
视觉一旦发现目标，就代表闸门已经开启或正在开启。
```

在这个前提下，原有的控制前提已经失效：

```text
RC 在线不能再作为连续运行硬门。
裁判在线不能再作为比赛中连续运行硬门。
裁判闸门状态不能再作为唯一闸门依据。
```

系统必须转为：

```text
视觉主导感知
内部状态机限制动作边界
超时机制负责失控兜底
RC/裁判如果恢复，只作为更高优先级的停机或强确认信号
```

## 2. 目标与非目标

### 目标

1. 在 RC 和裁判系统都收不到数据时，状态机仍能在视觉可靠的条件下完成自动流程。
2. 视觉发现目标可作为闸门开启证据，但不能直接等价为立即发射许可。
3. 第三发仍需要第二次开闸证据，不能取消 `gate_opening_count >= 2`。
4. 发射仍必须要求 `vision_target_aligned()`。
5. 保留发数限制、闸门窗口限制、3508 顶推完成限制和自动流程超时限制。

### 非目标

1. 不修改视觉协议结构。
2. 不取消现有裁判系统逻辑；裁判如果恢复在线，仍可作为强信号使用。
3. 不把 `vision_target_found` 当成最终发射对准条件。
4. 不重构整套状态机，只做围绕失联场景的局部改造建议。

## 3. 当前代码的主要问题

### 3.1 RC 断连会直接停机

当前 `shoot()` 和 `shoot_rc()` 中存在连续 RC 硬门：

```text
dart_rc_control_enabled() == false
    -> dart_enter_safe_stop()
    -> 状态机回到 IDLE
    -> 闸门计数和窗口状态被清空
```

在强干扰现场，RC 断连不应直接等价为“用户要求停机”。否则状态机永远无法启动，或者运行中被反复拉回 `IDLE`。

### 3.2 裁判掉线会让比赛状态失效

当前 `dart_game_started()` 依赖裁判在线和 `PROGRESS_BATTLE`。裁判系统收不到数据时：

```text
dart_game_started() == false
dart_gate_status_open() == false
dart_prepare_start_allowed() == false
dart_referee_allow_launch() == false
```

结果是准备动作和发射动作都无法继续。

### 3.3 视觉数据被 RC/裁判状态反向卡住

当前视觉链路存在两个风险：

| 位置 | 问题 |
|------|------|
| `usbv_task.c` | 如果 `accept_yaw` 依赖 RC/裁判，可能在 USB 入口清零 `vision_packet.state` |
| `shoot_task.c` | `vision_target_found_valid()` 如果依赖 `dart_rc_control_enabled()` 和 `dart_game_started()`，视觉兜底会失效 |

在本方案前提下，视觉是唯一可靠输入，因此视觉原始有效性必须独立于 RC 和裁判。

### 3.4 第三发仍可能卡住

第三发当前依赖：

```text
current_dart == 2 时，gate_opening_count >= 2
```

如果只依赖裁判 `1 -> 2` 边沿，在裁判系统收不到数据时，第二次开闸证据无法产生，第三发会卡在等待条件上。

## 4. 核心设计原则

### 4.1 输入职责重新定义

| 输入 | 原职责 | 新职责 |
|------|--------|--------|
| RC | 连续心跳，断了就停 | 若恢复在线，可作为最高优先级停机输入 |
| 裁判系统 | 比赛阶段、闸门状态、发射窗口硬依据 | 若恢复在线，可作为强确认信号 |
| 视觉 | 目标识别和对准 | 目标识别、闸门开启证据、最终对准判断 |

### 4.2 视觉语义必须拆开

| 视觉信号 | 语义 | 用途 |
|----------|------|------|
| `vision_target_found` | 看到目标，代表闸门已开或正在开 | 准备启动、开闸事件来源 |
| `vision_target_found` 的 `0 -> 1` 边沿 | 一次新的视觉开闸事件 | 增加 `gate_opening_count`，清零 `gate_fire_count` |
| `vision_target_found` 持续为 1 | 当前目标仍可见 | 允许视觉闸门窗口继续有效 |
| `vision_target_aligned()` | 目标正对 | 最终发射硬条件 |

不能混用：

```text
found 只说明看到了目标和闸门证据。
aligned 才说明允许发射。
```

### 4.3 裁判是强信号，视觉是弱信号

如果裁判系统未来恢复在线：

```text
裁判确认 dart_launch_opening_status == 0
    -> 闸门已完全打开
    -> 不需要额外等待
```

如果只能依赖视觉：

```text
视觉发现目标
    -> 闸门已开或正在开
    -> 必须等待 1000ms 后才允许进入发射判断
```

## 5. 推荐的系统状态语义

建议引入或明确以下概念：

| 概念 | 作用 |
|------|------|
| `dart_system_enabled()` | 当前系统是否允许自动流程运行，替代 RC 连续在线硬门 |
| `vision_target_raw_valid()` | 只判断视觉原始目标是否有效，不依赖 RC/裁判 |
| `vision_gate_event` | 视觉 `target_found 0 -> 1` 产生的一次开闸事件 |
| `vision_gate_ready` | 视觉开闸事件后已等待 1000ms，且目标仍有效 |
| `referee_gate_ready` | 裁判在线且确认闸门完全打开 |
| `gate_fire_ready` | 当前是否允许进入发射判断 |

建议关系：

```text
gate_fire_ready = referee_gate_ready || vision_gate_ready
```

在裁判完全收不到时，`gate_fire_ready` 主要由 `vision_gate_ready` 提供。

## 6. 具体修改建议

### 6.1 USB 层保留视觉原始数据

涉及文件：

```text
MDK-ARM/usbv_task.c
```

建议：

```text
USB 层只负责解析和保存视觉原始数据。
不要因为 RC/裁判失联而清零 vision_packet.state。
```

`accept_yaw` 可以继续反馈给视觉上位机，但不能反过来销毁视觉输入。

### 6.2 拆出视觉 raw 判断

涉及文件：

```text
MDK-ARM/shoot_task.c
MDK-ARM/visionv_task.c
```

建议新增或重定义：

```text
vision_target_raw_valid()
```

它只判断：

```text
vision_packet.state == 1
vision_control.target.target_found == 1
视觉更新时间未超时
```

不应依赖：

```text
dart_rc_control_enabled()
dart_game_started()
referee_is_online()
```

### 6.3 重新定义系统授权

涉及文件：

```text
MDK-ARM/shoot_task.c
```

建议新增：

```text
dart_system_enabled()
```

在 RC 和裁判都收不到的前提下，它应表达：

```text
自动流程已经授权启动
&& current_dart < DART_MAX_COUNT
&& 自动流程未超时
&& 视觉数据仍然有效
```

如果 RC 恢复在线并拨到安全档，应立即停机。

### 6.4 明确启动授权来源

由于 RC 和裁判都收不到，系统必须有新的启动授权来源。

推荐顺序：

| 方案 | 推荐度 | 说明 |
|------|--------|------|
| 物理开关/拨码/按键授权 | 最高 | 和无线干扰无关，最清晰 |
| 视觉目标连续有效启动 | 中 | 不加硬件，但需要严格超时 |
| 上电默认允许自动流程 | 低 | 风险最高，不建议作为默认方案 |

如果没有新增硬件，建议使用：

```text
视觉连续 N 帧发现目标
&& 当前流程未启动
&& current_dart == 0
```

作为本轮自动流程启动授权。

### 6.5 使用视觉 found 边沿作为开闸事件

涉及文件：

```text
MDK-ARM/shoot_task.c
```

建议：

```text
vision_found_now = vision_target_raw_valid()

如果 vision_found_now == 1 且 vision_found_last == 0：
    认为发生一次视觉开闸事件
    gate_opening_count++
    gate_fire_count = 0
    记录 vision_gate_open_tick

vision_found_last = vision_found_now
```

注意：

```text
只能用 0 -> 1 边沿增加 gate_opening_count。
不能用 target_found 持续为 1 每帧刷新 gate_fire_count。
```

### 6.6 视觉路径发射前等待 1000ms

建议新增宏：

```c
#define VISION_GATE_OPEN_DELAY_MS 1000
```

视觉路径的闸门许可：

```text
vision_gate_ready =
    vision_found_now
    && vision_gate_open_tick != 0
    && now - vision_gate_open_tick >= VISION_GATE_OPEN_DELAY_MS
```

原因：

```text
视觉发现目标代表闸门已开或正在开。
但为了防止闸门机械动作未完全打开，视觉路径必须等待 1000ms。
```

### 6.7 视觉开闸事件加冷却

建议新增宏：

```c
#define VISION_GATE_EVENT_COOLDOWN_MS 1500
```

建议条件：

```text
vision_found_now
&& !vision_found_last
&& now - last_vision_gate_event_tick >= VISION_GATE_EVENT_COOLDOWN_MS
```

作用：

```text
防止视觉画面抖动导致 gate_opening_count 重复增加。
```

### 6.8 视觉闸门窗口加超时

建议新增宏：

```c
#define VISION_GATE_WINDOW_TIMEOUT_MS 5000
```

建议语义：

```text
如果视觉开闸事件发生后长时间未发射：
    vision_gate_ready = false
```

这样可以避免一次视觉开闸事件长期有效。

### 6.9 第三发仍保留第二次开闸要求

第三发约束必须保留：

```text
if current_dart == 2:
    gate_opening_count >= 2
```

区别是：

```text
裁判可用时，gate_opening_count 可由裁判 1 -> 2 边沿增加。
裁判不可用时，gate_opening_count 由视觉 target_found 0 -> 1 边沿增加。
```

第三发不能因为 `target_found` 持续为 1 直接通过，必须看到第二次有效视觉开闸事件。

### 6.10 状态机不能因 RC/裁判失联直接回 IDLE

建议：

```text
自动流程已启动后：
    RC 断连不直接 safe stop
    裁判掉线不清空 gate_opening_count
    视觉仍有效且流程未超时，则状态机继续运行
```

停机条件改为：

```text
四发完成
自动流程总超时
视觉丢失超过超时
RC 恢复在线且拨到安全档
裁判恢复在线且明确进入非比赛阶段
```

## 7. 推荐发射条件

最终 `dart_referee_allow_launch()` 的建议语义：

```text
允许发射 =
    自动流程已经授权启动
    && current_dart < DART_MAX_COUNT
    && dart_match_fire_count < DART_MAX_COUNT
    && gate_fire_count < DART_GATE_MAX_FIRE_COUNT
    && up_hold_current_released == 1
    && gate_fire_ready == true
    && 如果 current_dart == 2，则 gate_opening_count >= 2
    && vision_target_aligned() == true
    && 自动流程未超时
```

其中：

```text
gate_fire_ready =
    referee_gate_ready
    || vision_gate_ready
```

在 RC 和裁判都收不到时：

```text
referee_gate_ready 基本为 false
vision_gate_ready 是主要闸门依据
```

## 8. 推荐参数

| 参数 | 建议值 | 说明 |
|------|--------|------|
| `VISION_GATE_OPEN_DELAY_MS` | `1000` | 视觉发现目标后等待闸门完全打开 |
| `VISION_GATE_EVENT_COOLDOWN_MS` | `1500` | 防止视觉抖动重复计数 |
| `VISION_GATE_WINDOW_TIMEOUT_MS` | `5000-8000` | 防止一次开闸事件长期有效 |
| `VISION_LOST_STOP_TIMEOUT_MS` | `2000-3000` | 视觉短暂丢帧可容忍，长时间丢失停机 |
| `DART_AUTO_TOTAL_TIMEOUT_MS` | `60000-120000` | 防止无人控制下长期运行 |

已有的单状态超时，例如 `DOWN_TIMEOUT_MS`、`UP_TIMEOUT_MS`、`RELOAD_DOWN_TIMEOUT_MS`，建议继续保留。

## 9. 文件与函数对应表

| 文件 | 建议处理点 |
|------|------------|
| `MDK-ARM/usbv_task.c` | 不再因为 RC/裁判不可用清零 `vision_packet.state` |
| `MDK-ARM/visionv_task.c` | 视觉目标更新时间、目标有效性保持独立 |
| `MDK-ARM/shoot_task.c` | 新增 `vision_target_raw_valid()`、`dart_system_enabled()`、视觉开闸事件、视觉闸门延迟、自动流程超时 |
| `MDK-ARM/shoot_task.c` | 修改 `dart_prepare_start_allowed()`，允许视觉 raw 目标触发准备 |
| `MDK-ARM/shoot_task.c` | 修改 `dart_referee_allow_launch()`，使用 `gate_fire_ready` 替代单一裁判闸门判断 |
| `MDK-ARM/shoot_task.c` | 修改 `update_dart_match_control()`，裁判掉线不直接清空闸门计数 |
| `MDK-ARM/shoot_task.c` | 修改 `shoot()`，RC/裁判失联不直接拉回 `IDLE`，改由系统授权和超时控制 |

## 10. 推荐落地顺序

| 优先级 | 修改内容 | 原因 |
|--------|----------|------|
| 1 | USB 层不清零视觉数据 | 先保证唯一可靠输入不被截断 |
| 2 | 拆出视觉 raw 有效判断 | 让视觉脱离 RC/裁判硬门 |
| 3 | 引入系统授权和自动流程超时 | 解决无人控制下的运行边界 |
| 4 | 加入视觉 found 边沿开闸事件 | 解决裁判不可用时闸门证据缺失 |
| 5 | 加入 1000ms 视觉闸门延迟 | 避免闸门未完全打开就发射 |
| 6 | 加入 1500ms 冷却和窗口超时 | 防止视觉抖动和窗口假保持 |
| 7 | 调整第三发 gate_opening_count 来源 | 让第三发在裁判不可用时仍有开闸证据 |
| 8 | 调整发射许可为 `gate_fire_ready && vision_target_aligned()` | 保持发射安全边界 |

## 11. 必须保留的硬保护

以下保护不能取消：

| 保护 | 要求 |
|------|------|
| `current_dart < DART_MAX_COUNT` | 防止超过四发 |
| `dart_match_fire_count < DART_MAX_COUNT` | 防止比赛内发数超限 |
| `gate_fire_count < DART_GATE_MAX_FIRE_COUNT` | 防止单次闸门窗口内发射过多 |
| 第三发 `gate_opening_count >= 2` | 防止第三发提前发射 |
| `up_hold_current_released == 1` | 确保 700ms 顶推完成 |
| `vision_target_aligned() == true` | 最终发射对准硬门 |
| 自动流程总超时 | 防止失控长期运行 |
| 视觉丢失超时 | 防止视觉中断后继续发射 |

## 12. 验证清单

建议按以下场景验证：

| 场景 | 预期 |
|------|------|
| RC 和裁判都无数据，视觉无目标 | 不启动，不发射 |
| RC 和裁判都无数据，视觉发现目标但未正对 | 可准备，但不发射 |
| RC 和裁判都无数据，视觉发现目标且正对，未满 1000ms | 不发射 |
| RC 和裁判都无数据，视觉发现目标且正对，超过 1000ms | 允许进入发射 |
| 视觉 found 抖动 | 不重复增加 `gate_opening_count` |
| 第二次视觉开闸事件前进入第三发 | 第三发不发射 |
| 第二次视觉开闸事件后进入第三发 | 第三发允许进入发射判断 |
| 视觉丢失超过超时 | 停机或禁止发射 |
| 四发完成 | 停机并清零 |
| RC 恢复并拨到安全档 | 立即停机 |
| 裁判恢复并明确非比赛阶段 | 停机并清零 |

## 13. 最终结论

在“裁判系统数据和遥控器数据都收不到”的前提下，不应继续围绕 `dart_rc_control_enabled()` 和 `dart_game_started()` 修补，而应把控制模型改成：

```text
视觉 found 边沿 = 开闸事件
视觉 found 后等待 1000ms = 闸门发射许可
视觉 aligned = 最终发射许可
内部状态机 = 发数、流程、顶推和超时保护
```

最关键的安全边界是：

```text
视觉 found 可以让系统准备。
视觉 found 的边沿可以提供开闸次数。
视觉 found 后必须等待 1000ms。
真正发射必须 vision_target_aligned()。
第三发必须 gate_opening_count >= 2。
```

这样既能适应 RC/裁判都收不到的现场条件，也能避免因为视觉常亮、视觉抖动、闸门未完全打开或第三发证据不足导致误发射。
