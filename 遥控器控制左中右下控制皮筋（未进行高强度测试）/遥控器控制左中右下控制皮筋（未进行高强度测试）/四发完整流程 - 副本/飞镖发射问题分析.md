# 飞镖发射流程问题分析

> 原始现象描述：
> 1. 第一发飞镖在上膛时，因为3508突然下降，会有一个极大的力量，然后给飞镖震掉
> 2. 第三发的的流程有点问题，我的测试现象是，在第二次闸门数据没有时，视觉锁定到目标，直接发射了，没有等待一秒用来防止现实闸门没有完全开启
> 3. 在第二次闸门没有数据时，视觉先锁定到，执行无裁判系统的视觉流程时，第三发发射了，然后又接收到了闸门数据，机器会再次执行第三发的流程，但是此时第三发飞镖早就发射出去，就空放了，这个空放执行了视觉的等待一秒再发射，然后在执行第四发的流程

---

## 一、第一发飞镖上膛时被震掉的问题

### 1.1 现象

上膛（DOWN状态）时，3508电机突然施加较大电流，产生瞬间冲击力，导致飞镖从发射位被震落。

### 1.2 根因：斜坡函数的 min/max 参数语义导致瞬时电流跳变

关键代码路径：

**状态切换**（`shoot_task.c:1055-1075`，IDLE → DOWN）：
```c
ramp_init(&fire_left_down, 0.02, 14000.0f, DOWN_3508_MIN_CURRENT);
ramp_init(&fire_right_down, 0.02, -DOWN_3508_MIN_CURRENT, -14000.0f);
```
其中 `DOWN_3508_MIN_CURRENT = 6000`（mA）。

**斜坡函数实现**（`user_lib.c:15-36`）：

```c
void ramp_init(ramp_function_source_t *ramp_source_type, fp32 frame_period,
               fp32 max, fp32 min) {
    ramp_source_type->max_value = max;
    ramp_source_type->min_value = min;
    ramp_source_type->out = 0.0f;   // <-- 输出从 0 开始
}

void ramp_calc(ramp_function_source_t *ramp_source_type, fp32 input) {
    ramp_source_type->out += input * frame_period;   // 每次加 110*0.02=2.2
    if (out > max) out = max;
    else if (out < min) out = min;                  // <-- 关键：低于 min 直接拉到 min
}
```

**问题**：`ramp_init` 设定 `out = 0`。第一个周期调用 `ramp_calc` 后，`out = 0 + 2.2 = 2.2`，这 **小于 `min_value = 6000`**，所以 `out` 被直接钳位到 6000。左右两个 3508 电机同时从 0mA 跳变到 ±6000mA，产生一个没有渐变过程的阶跃力矩冲击。

同样的模式也出现在上抬（UP）方向：
```c
ramp_init(&fire_left, 0.02, 0.0f, -UP_3508_FAST_CURRENT);   // min=-6500, out 从0→跳变到-6500
ramp_init(&fire_right, 0.02, 0.0f, UP_3508_FAST_CURRENT);    // max=6500, out 从0→跳变到6500
```

### 1.3 为什么第一发尤其严重

在 `handle_down_movement` 中（`shoot_task.c:1125-1153`）：

```c
uint8_t first_shot_learning = (Dart_Data.current_dart == 0 && !learned_down_valid);
uint32_t down_timeout = first_shot_learning ? FIRST_SHOOT_LOCK_DELAY_MS : DOWN_TIMEOUT_MS;
// FIRST_SHOOT_LOCK_DELAY_MS = 3800ms, DOWN_TIMEOUT_MS = 6500ms
```

第一发飞镖走学习路径（`first_shot_learning = true`），此路径下 `motion_arrive_confirmed` 被强制返回 0：
```c
uint8_t arrive_confirmed = first_shot_learning ? 0 : motion_arrive_confirmed(latch_pressed);
```

这意味着第一发下压全程依赖 3800ms 纯超时，不检查行程到位。即使物理上已经顶到底部，电机仍然维持大电流（从 6000 一路斜坡到 14000），额外的大电流冲击可能造成机构弹跳。

另外，第一发时 `learned_down_valid = false`，`get_down_travel_ref()` 返回的是写死的 `TRAVEL_DOWN = 848000` 脉冲，与实际机构行程可能不匹配，导致到位判定和力学特性更差。

### 1.4 修复建议

修改 `ramp_init` 的语义：由于代码中用 `min_value` 来表示 "初始电流值"（如 `DOWN_3508_MIN_CURRENT = 6000`），需要让 `out` 的初始值直接设为 `min`（正值情况）或 `max`（负值情况），而不是 0。或者在 `shoot_task.c` 层面，把 DOWN 的初始电流从 6000 减小，或者增加一个从 0 缓慢斜坡到 6000 的阶段。

## 二、第三发视觉流程中"直接发射，未等待一秒"的问题

### 2.1 现象

第二次闸门无裁判数据时，视觉识别到目标后，第三发飞镖没有经过 1000ms 延时就直接发射了。

### 2.2 根因：`vision_gate_open_tick` 在飞镖之间未清零

关键变量 `vision_gate_open_tick`（`shoot_task.c:348`）用于记录视觉锁定到目标时的系统 tick，配合 `VISION_GATE_OPEN_DELAY_MS = 1000` 实现 "视觉锁定后等待 1 秒再允许发射" 的安全延时。

**它的设置时机** 仅在 `update_dart_auto_control()` 中（`shoot_task.c:744-751`）：

```c
// 视觉上升沿：目标从"未找到"→"找到"
if (vision_found_now && !vision_found_last && ...) {
    vision_gate_open_tick = now;       // 仅在上升沿更新
    last_vision_gate_event_tick = now;
    ...
}
```

**它的清零时机** 仅在 `reset_dart_window_control()` 中（`shoot_task.c:785-798`）：
```c
vision_gate_open_tick = 0;  // 只在 safe_stop 和 shoot_init 时调用
```

**问题场景**：

1. 第二发飞镖（`current_dart == 1`）在 WAIT_GATE 状态时，视觉锁定了目标，产生上升沿，`vision_gate_open_tick = T0`。
2. 第二发发射 → 下压后发射 → 步进换弹 → 取镖 → 上抬（第三发），整个流程中 **视觉持续锁定目标，没有丢失过**，所以没有新的上升沿，`vision_gate_open_tick` 一直等于 `T0`。
3. 第三发（`current_dart == 2`）进入 WAIT_GATE 状态时，`dart_gate_fire_ready()` 检查：
   ```c
   if (vision_gate_open_tick != 0 &&                          // T0 ≠ 0，通过
       vision_target_raw_valid() &&                           // 视觉仍在锁定，通过
       (now - vision_gate_open_tick) >= VISION_GATE_OPEN_DELAY_MS &&  // now - T0 >> 1000ms，通过！
       (now - vision_gate_open_tick) <= VISION_GATE_WINDOW_TIMEOUT_MS) // 仍需在6000ms窗口内
   ```
4. 如果从第二发视觉锁定到第三发进入 WAIT_GATE 的间隔 < 6000ms（`VISION_GATE_WINDOW_TIMEOUT_MS`），则 1000ms 延时被 **瞬间满足**，`dart_gate_fire_ready()` 直接返回 true，飞镖发射。

本质上，`vision_gate_open_tick` 是一个"跨飞镖持久"的变量，而它应该"每发飞镖独立"。第二发期间的视觉锁定时戳被第三发继承，导致第三发直接清除了本应独立计时的 1 秒等待。

### 2.3 修复建议

在每次新飞镖进入 WAIT_GATE 或 DOWN 状态时，将 `vision_gate_open_tick` 清零，确保每发飞镖独立等待 1 秒。例如在 `DART_STATE_IDLE → DART_STATE_DOWN` 的转换处，或 `DART_STATE_UP → DART_STATE_WAIT_GATE` 的转换处。

## 三、第三发发射后裁判闸门数据迟到导致的"空放"问题

### 3.1 现象

在第二次闸门无数据时，视觉流程正常触发了第三发发射。之后裁判系统的闸门数据延迟到达（`dart_launch_opening_status` 从 1→2 的边沿），触发了一次新的发射流程，但第三发飞镖已经射出，成为一次空放。空放结束后继续进入第四发流程。

### 3.2 根因：裁判闸门边沿与视觉闸门事件"双重计数"且`gate_fire_count`被复位

这个问题的链条比较长，逐层分析：

#### 3.2.1 `gate_opening_count` 的双重计数

`gate_opening_count` 在两个地方递增（针对"第二次闸门"这同一个物理事件）：

**(A) 裁判路径** — `update_dart_match_control()`（`shoot_task.c:718-731`）：
```c
gate_opening_edge_latched = (last_dart_launch_opening_status == 1 &&
    referee_data.dart_launch_opening_status == 2);  // 1→2 边沿
if (gate_opening_edge_latched) {
    gate_opening_count++;        // 裁判闸门事件 +1
    gate_fire_count = 0;
}
```

**(B) 视觉路径** — `update_dart_auto_control()`（`shoot_task.c:744-758`）：
```c
if (vision_found_now && !vision_found_last && ...) {
    // 视觉锁定上升沿 = 视为一次闸门事件
    gate_opening_count++;        // 视觉闸门事件 +1
    gate_fire_count = 0;
}
```

两者各自独立触发，将同一个物理闸门开启算了两次 `gate_opening_count`。比如：
- 第一闸门（裁判数据正常）：`gate_opening_count = 1`
- 第二闸门（无裁判数据）：视觉上升沿 → `gate_opening_count = 2`
- 第二闸门（裁判数据迟到）：1→2 边沿 → `gate_opening_count = 3`

第三发检查 `gate_opening_count >= 2` 通过后发射，然后裁判数据迟到再次递增，为后续的异常埋下种子。

#### 3.2.2 `gate_fire_count` 被裁判迟到数据意外复位

裁判闸门边沿事件中（`shoot_task.c:720-731`）：
```c
if (gate_opening_edge_latched) {
    gate_opening_count++;
    gate_fire_count = 0;    // <-- 无条件下复位
}
```

`gate_fire_count` 的语义是"当前闸门窗口内已发射次数"，上限为 `DART_GATE_MAX_FIRE_COUNT = 2`（每个闸门窗口最多 2 发）。

正常流程：第二闸门窗口内发射第三发和第四发，`gate_fire_count` 从 0→1→2。

异常流程：
1. 第三发通过视觉流程发射 → `gate_fire_count` 从 0 变为 1。
2. 裁判闸门数据迟到到达（1→2 边沿）→ `gate_fire_count` 被 **无条件复位为 0**。
3. 第四发加载完成进入 WAIT_GATE → `dart_referee_allow_launch()` 检查 `gate_fire_count >= 2` → 不满足（现在是 0）→ 允许发射。

此时闸门可能仍然打开（裁判状态 `dart_launch_opening_status == 0`），第四发立即发射。

#### 3.2.3 用户观察到的"空放第三发"是如何发生的

这里的关键是理解用户观察到的时序。考虑一个更具体的场景：

**如果第三发通过视觉路径进入 LAUNCH 状态后，在 `handle_launch()` 的前 100ms 内（`state_timer <= LAUNCH_READY_DELAY_MS`），裁判闸门数据也到达了**：

`handle_launch()` 中（`shoot_task.c:1250-1304`）：
```c
if (Dart_Data.state_timer <= LAUNCH_READY_DELAY_MS &&
    !dart_referee_allow_launch())     // 视觉路径下，裁判闸门未到，此条件为 true
{
    stop_and_wait_gate();             // <-- 返回 WAIT_GATE，current_dart 未++
    return;
}
```

但在裁判数据迟到的情况下，`dart_referee_allow_launch()` 可能仍然返回 false（因为裁判闸门边沿 1→2 只是意味着"正在开启"，`dart_launch_opening_status == 2`，而不是 `== 0` 已开启）。此时 `stop_and_wait_gate()` 被调用，状态回到 WAIT_GATE，`current_dart` 仍为 2。

随后裁判闸门完全打开（`dart_launch_opening_status: 2→0`），`dart_gate_status_open()` 返回 true，`dart_referee_allow_launch()` 变为 true，状态再次进入 LAUNCH，**但此时舵机已在第一轮 LAUNCH 阶段松开了飞镖，第三发已经射出去了**——机器人执行了一次完整的空放动作。

另一种更简单的场景：第三发通过视觉路径完整发射（`current_dart: 2→3`，`gate_fire_count: 0→1`），然后进入 DOWN_AFTER_LAUNCH → STEPPER_MOVE（送第四发）→ ...。在步进电机送弹期间，裁判闸门 1→2 边沿到达，`gate_fire_count` 被复位为 0，`gate_opening_count++`。等到第四发进入 WAIT_GATE 时，闸门已开（`dart_launch_opening_status == 0`），直接发射。用户看到的时序是：第三发射出 → 短暂间隔 → 又一次发射（实际是第四发）→ 步进换弹（实际没有第五发，所以空转）。由于整个流程紧凑，用户感知为"第三发空放 + 第四发正常"。

### 3.3 总结三个核心缺陷

| 编号 | 缺陷 | 所在位置 | 影响 |
|------|------|----------|------|
| ① | `vision_gate_open_tick` 跨飞镖未清零 | `shoot_task.c:348`, `update_dart_auto_control()` | 第三发继承第二发的视觉锁定时戳，跳过 1 秒安全延时 |
| ② | `gate_opening_count` 被裁判和视觉双路径重复递增 | `update_dart_match_control():727`, `update_dart_auto_control():755` | 闸门事件计数虚高，第三发条件提前满足 |
| ③ | `gate_fire_count` 被迟到裁判数据无条件复位 | `update_dart_match_control():728` | 打破 `DART_GATE_MAX_FIRE_COUNT` 限次，允许额外发射 |

这三个缺陷相互作用，导致了用户观察到的完整异常：视觉锁定后第三发跳过 1 秒等待直接发射 → 裁判数据迟到后 `gate_opening_count` 额外递增且 `gate_fire_count` 复位 → 后续飞镖的发射逻辑被打乱 → 出现空放。

### 3.4 修复建议

1. **在每发飞镖开始时重置 `vision_gate_open_tick`**：在 `DART_STATE_IDLE → DART_STATE_DOWN` 转换处，或至少在每个 dart 到达 WAIT_GATE 时重置，确保每发飞镖独立等待 1 秒。

2. **防止 `gate_opening_count` 双重计数**：`update_dart_auto_control()` 中通过视觉上升沿递增 `gate_opening_count` 时，应检查是否在短时间内已有裁判闸门边沿事件。或者建立统一的"闸门事件"抽象，裁判和视觉共享同一个事件源。

3. **`gate_fire_count` 不应无条件复位**：在 `update_dart_match_control()` 中，当裁判闸门边沿到达时，应检查 `dart_match_fire_count` 或 `current_dart` 的状态，避免在已有飞镖射出后仍然复位 `gate_fire_count`。例如只有在 `gate_fire_count == 0` 时才复位，或者将复位条件与飞镖发射进度关联。

4. **在 `handle_launch()` 中增加"已发射"保护**：防止 LAUNCH 状态因条件变化而返回 WAIT_GATE 后再次进入 LAUNCH（如果舵机已经释放过）。增加一个标志位标记舵机是否已经执行过释放动作。

## 四、我的判断：根本原因不是单一 bug，而是"事件归属"和"状态边界"没有定义清楚

我认为这次现象的直接原因可以分成前面三类：3508 电流阶跃、视觉等待时间戳未按飞镖隔离、裁判闸门迟到后又触发一次流程。但更深一层看，它们其实来自同一种设计问题：代码没有把"一次闸门开启事件"、"当前正在处理第几发飞镖"、"本发飞镖是否已经实际释放"这几个概念绑定成一个明确的状态边界。

现在的逻辑更像是多个全局变量在共同决定是否允许发射：

- `gate_opening_count` 记录闸门开启次数；
- `gate_fire_count` 记录当前闸门窗口内已发射次数；
- `vision_gate_open_tick` 记录视觉锁定时间；
- `current_dart` 记录当前飞镖序号；
- 裁判系统和视觉系统都可以改变这些变量。

这些变量单独看都有意义，但它们没有被绑定到同一个"事件实例"上。例如第二次闸门开启这件事，视觉先认为它发生了，裁判数据迟到后又认为它发生了一次。代码没有判断"这是不是同一个物理闸门事件"，所以就出现了重复计数、重复复位、重复发射。

我的核心判断是：**系统缺少一个统一的闸门事件仲裁层**。视觉数据和裁判数据本质上都是在描述同一个外部事实：闸门是否已经打开。它们不应该分别直接修改发射流程的关键计数，而应该先合并成一个经过消抖、去重、带来源标记的"闸门窗口"。发射状态机只消费这个统一后的闸门窗口。

另外，当前 LAUNCH 状态对"飞镖已经被舵机释放"这件事没有硬边界。只要发射条件发生变化，状态仍可能退回 WAIT_GATE，再次进入 LAUNCH。机械上飞镖一旦释放，这就是不可逆动作；软件状态机也应该把它当成不可逆边界。否则只要裁判数据、视觉数据、电机状态在几十到几百毫秒内交错到达，就容易出现"软件以为还没发，机械已经发了"的错位。

所以我更倾向于把原因归纳为：

1. **电机控制层的问题**：斜坡函数的 `min/max` 使用方式导致初始输出不是平滑变化，而是直接跳到最小工作电流，引起第一发震动。
2. **感知融合层的问题**：视觉和裁判系统没有统一仲裁，同一个闸门事件可能被统计两次。
3. **发射状态机的问题**：每发飞镖的临时状态没有独立生命周期，上一发的视觉时间戳、闸门窗口、发射计数会影响下一发。
4. **机械动作不可逆边界缺失**：舵机释放飞镖后，软件没有立即锁定"本发已释放"，导致条件变化时可能重复执行发射流程。

如果只修某一个点，例如只清零 `vision_gate_open_tick`，第三发不等 1 秒的问题会缓解，但裁判数据迟到后的重复计数和复位仍然可能在其他时序下复现。比较稳的修法应该是：先给每一次闸门开启生成一个唯一的 gate window，再让每一发飞镖绑定到某个 gate window，并且在舵机释放后立刻标记本发完成。这样视觉迟到、裁判迟到、持续锁定、短暂丢帧，都不会轻易把状态机带回已经经过的阶段。

我认为这次故障最可能的本质不是参数调得不合适，而是异步事件进入状态机时缺少去重和生命周期管理。机械系统里，"闸门开了"和"飞镖发了"都是物理世界的一次性事件；软件也必须把它们建模成一次性事件，而不能只靠几个可被反复覆盖的全局变量来推断。

## 五、继续检查后发现的补充风险点

下面这些问题不一定已经直接造成了这次现象，但它们和当前异常属于同一类时序风险。如果只修前面三个明显 bug，而不处理这些边界情况，后续仍可能在不同测试条件下复现类似的"提前发射"、"重复发射"或"机械震动"。

### 5.1 视觉短暂丢失后重新锁定，仍可能跳过 1 秒等待

`update_dart_auto_control()` 里视觉事件的触发条件不仅要求 `vision_found_now && !vision_found_last`，还要求距离上一次视觉闸门事件超过 `VISION_GATE_EVENT_COOLDOWN_MS = 1500`：

```c
if (vision_found_now &&
    !vision_found_last &&
    (last_vision_gate_event_tick == 0 ||
     (now - last_vision_gate_event_tick) >= VISION_GATE_EVENT_COOLDOWN_MS))
{
    vision_gate_open_tick = now;
    last_vision_gate_event_tick = now;
    ...
}
```

这个逻辑可以防止视觉抖动导致重复计数，但也带来一个副作用：如果视觉目标短暂丢失后很快恢复，例如丢失 100ms、300ms 或 800ms，由于还在 1500ms 冷却时间内，`vision_gate_open_tick` 不会更新。随后 `vision_found_last` 被置回 1，之后也不会再产生新的上升沿。

结果是：重新锁定目标后，系统仍然沿用旧的 `vision_gate_open_tick`。如果旧时间戳已经超过 1000ms，`dart_gate_fire_ready()` 会立刻认为视觉等待已经满足。也就是说，**短暂丢帧后的重新锁定，不一定会重新等待 1 秒**。

这和前面第二节的"跨飞镖继承视觉时间戳"很像，只是这里不是跨飞镖，而是跨一次短暂丢帧。实际比赛中视觉数据很容易因为目标遮挡、车体震动、通信抖动出现短暂无效，这个风险不能忽略。

建议：视觉丢失时至少要清除或失效 `vision_gate_open_tick`，或者记录"连续稳定识别开始时间"，而不是只记录第一次上升沿。发射前应满足"当前这一段连续有效视觉已经持续 1000ms"，而不是"历史上某次视觉事件已经过去 1000ms"。

### 5.2 1500ms 去重窗口不足以彻底解决裁判数据迟到

当前代码里已经有一个 `last_gate_open_event_tick`，裁判路径和视觉路径都会检查：

```c
if (last_gate_open_event_tick == 0 ||
    (now - last_gate_open_event_tick) >= VISION_GATE_EVENT_COOLDOWN_MS)
{
    gate_opening_count++;
    gate_fire_count = 0;
    last_gate_open_event_tick = now;
}
```

这个机制可以挡住一部分"视觉刚触发，裁判马上迟到"的重复计数。但它只靠 1500ms 时间窗口判断两个事件是不是同一次闸门开启。问题是，前面定义的视觉闸门窗口是 `VISION_GATE_WINDOW_TIMEOUT_MS = 6000`，也就是说软件承认一次视觉闸门事件最长可以影响 6 秒；但去重只保护 1.5 秒。

如果视觉先识别到目标并把第二次闸门算作一次事件，裁判数据在 2 秒、3 秒甚至 5 秒后才到达，那么它仍然会通过 1500ms 冷却检查，再次执行：

- `gate_opening_count++`
- `gate_fire_count = 0`
- `last_gate_open_event_tick = now`

所以 1500ms 冷却只能缓解迟到很短的情况，不能从逻辑上证明"视觉事件和裁判事件是同一个物理闸门事件"。这也是我认为需要 gate window 概念的原因：去重不应该只看时间间隔，而应该看当前是否已经存在一个未关闭、未过期、未消费完的闸门窗口。

建议：如果当前已经有一个 active gate window，而且还在 6000ms 有效期内，迟到的裁判边沿只能补充该窗口的来源信息，不能再次增加 `gate_opening_count`，更不能重置 `gate_fire_count`。

### 5.3 WAIT_GATE 阶段的顶部保持动作可能引入额外发射前扰动

`DART_STATE_WAIT_GATE` 中每一轮都会调用 `hold_3508_up()`：

```c
case DART_STATE_WAIT_GATE:
    hold_3508_up();
    if (dart_referee_allow_launch())
    {
        Dart_Data.dart_state = DART_STATE_LAUNCH;
        Dart_Data.state_timer = 0;
    }
    break;
```

`hold_3508_up()` 的逻辑不是简单断电等待，而是先用 `UP_3508_HOLD_CURRENT = 500` 等待顶部稳定，然后再用 `UP_3508_TOP_PUSH_CURRENT = HOLD_CURRENT = 7000` 顶住 `UP_3508_TOP_PUSH_MS = 700`，最后才释放电流：

```c
if (up_hold_push_count < UP_3508_TOP_PUSH_MS)
{
    up_hold_push_count++;
    CAN_Cmd3508(-UP_3508_TOP_PUSH_CURRENT, UP_3508_TOP_PUSH_CURRENT, 0, 0);
}
else
{
    up_hold_current_released = 1;
    CAN_Cmd3508(0, 0, 0, 0);
}
```

这意味着飞镖进入 WAIT_GATE 后，机械上还会有一段顶部顶紧动作。如果飞镖已经处在比较敏感的临界位置，或者舵机锁止余量不够，这 700ms 的 7000mA 顶推可能造成额外振动。它不一定会像第一发下压那样直接把飞镖震掉，但会增加"等待闸门阶段飞镖姿态变化"的可能性。

更关键的是，`dart_referee_allow_launch()` 又要求：

```c
if (!up_hold_current_released)
    return 0;
```

所以发射许可不仅取决于闸门和视觉，也取决于顶部保持动作是否完成。这个条件本身是合理的，但它把机械顶紧流程和闸门等待流程耦合在一起：闸门已经开、视觉已经对准时，系统仍可能因为顶部保持没结束而继续顶；顶部保持刚结束时，又可能立刻进入 LAUNCH。这个边界最好实测确认是否会带来飞镖轻微位移。

建议：记录 WAIT_GATE 内 3508 电流释放时刻与 LAUNCH 开始时刻，观察两者之间是否总是紧贴。如果紧贴，可以考虑在 `up_hold_current_released` 后增加一个很短的机械稳定确认，或者降低顶部顶推电流/时间。

### 5.4 延时计数和斜坡周期的时间基准不统一，参数很容易误判

`shoot_task()` 最后是：

```c
vTaskDelay(1);
```

状态机里的 `Dart_Data.state_timer++` 基本按 1ms 计数，所以 `LAUNCH_READY_DELAY_MS = 100`、`STEPPER_MOVE_WAIT_MS = 3000` 这些宏名和实际循环是一致的。

但斜坡函数初始化时大量使用 `frame_period = 0.02`：

```c
ramp_init(&fire_left_down, 0.02, 14000.0f, DOWN_3508_MIN_CURRENT);
ramp_init(&fire_right_down, 0.02, -DOWN_3508_MIN_CURRENT, -14000.0f);
```

如果 `ramp_calc()` 实际也是每 1ms 调一次，那么 `0.02` 就不是实际调用周期。这样一来，`ramp_calc(&fire_left_down, 110.0f)` 的真实含义会变得很难直觉判断：它不是"每 20ms 增加一次"，而是"每 1ms 按 0.02 的系数增加一次"。最终电流变化速度取决于任务循环频率、`frame_period` 和 input 三者共同作用。

这个问题不一定是当前故障的直接原因，但它会让调参非常容易误判。例如以为某个斜坡需要几秒，实际可能因为调用频率不同而快很多或慢很多。对发射机构这种强机械耦合系统来说，时间基准不统一会放大震动和到位判断的不确定性。

建议：要么让 `frame_period` 使用真实任务周期，例如 0.001；要么不要在这里使用"秒"语义，直接把 `input` 定义为每周期增量。无论选哪种，都应该让宏名和注释明确写出单位，避免之后继续靠经验试参数。

### 5.5 第一发学习流程把"学习"和"执行"绑在一起，失败时没有降级保护

第一发下压时：

```c
uint8_t first_shot_learning = (Dart_Data.current_dart == 0 && !learned_down_valid);
uint8_t arrive_confirmed = first_shot_learning ? 0 : motion_arrive_confirmed(latch_pressed);
uint32_t down_timeout = first_shot_learning ? FIRST_SHOOT_LOCK_DELAY_MS : DOWN_TIMEOUT_MS;
```

这等于第一发学习阶段完全不使用到位确认，只靠 3800ms 超时完成。随后 `learn_bottom_position()` 会把当前编码器位置学习成底部参考。如果第一发因为飞镖被震掉、机构卡滞、编码器异常、或者实际还没到稳定底部就进入学习，那么后面的 `reload_bottom_pos_1/2`、`learned_down_travel` 都可能建立在一个错误位置上。

也就是说，第一发异常不仅影响第一发本身，还可能污染后续三发的行程参考。前文已经提到第一发震动更明显，这里补充的是：**第一发一旦异常，后续的到位判断也可能被带偏**。

建议：学习底部位置时不要只依赖固定时间，应至少要求两个条件同时满足：编码器行程达到合理区间、双 3508 速度低于阈值并稳定一段时间。如果学习失败，就不要置 `learned_down_valid = 1`，后续流程应进入安全停止或保守参数，而不是继续把错误位置当作基准。
